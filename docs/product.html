Identity paths are symmetric questions — “how are these IDs connected?” Lineage is directional — “where can this object flow or originate?” The tool keeps those questions separate.

Why it exists

Cross-system investigations usually begin with exports and a simple-looking ID question. The complexity appears when normalization, composite keys, partner relationships, one-to-many mappings, and multiple migration stages enter the picture.

01

Make identity explicit

Build canonical IDs and typed relationships from ordinary exports with declared normalization rather than hidden heuristics.

02

Expose ambiguity

Identity collisions, conflicting attributes, cardinality violations, duplicates, orphans, and broken references become diagnostics instead of silent merges.

03

Trace with provenance

Paths and lineage carry relationship types plus file, worksheet, and row references so a finding can be checked against the source export.

Useful before you have an API

The product deliberately accepts the artifacts enterprise teams can usually obtain: CSV and XLSX. Vendor-specific exports stay at the boundary while the analysis model remains reusable. The public example is a generated bounded investigation with its exact graph and integrity manifest.

Build and investigate

python -m pip install .

  --focus AFS:4711 --policy examples/identity-policy.json
data-relationship-map handoff build customer-model.json handoff \
  --focus AFS:4711 --policy examples/identity-policy.json
data-relationship-map handoff verify handoff

Policy matters too

Explicit cardinality rules can say that `mapped_to` must be 1:1 while a `ship_to` relationship remains unrestricted. Snapshot diff makes relationship and orphan drift visible over time.

Not a master-data hub and not an ETL engine. It is an investigation and assurance graph built from supplied exports and explicit relationship rules.

Where it connects
